# Migrate an Bedrock Panel drop-in app between repos

An Bedrock Panel community app is self-contained under `community-apps/<id>/`, catalogued by
`community-apps/index.json` (generated by `tools/build-community-index.js`), and shipped with
a committed `<id>.zip` sitting next to the app folder. Moving an app between repos means
reproducing exactly those three things in the target and (for a move) removing them from the
source.

Publishing to a **public** repo is outward-facing and hard to reverse. Confirm the user
wants the public publish, confirm the two workflow decisions (**remove from source or keep
in both?** and **push straight to the target's main or via a branch/PR?**), and verify the
app ships no secrets — before you push.

## Pre-flight (do this first, every time)

1. **Identify both repos and their remotes.** For each, `git -C <repo> remote -v`. A public
   Bedrock Panel clone often has TWO remotes: `origin` (the user's repo, e.g.
   `github.com/TeeJS/bedrock-panel`) and `fork` (the upstream it was forked from). **Push only
   to the user's remote.** Confirm the branch and its upstream:
   `git -C <target> rev-parse --abbrev-ref main@{upstream}` should read `origin/main`. Push
   explicitly (`git push origin main`) — never rely on default tracking when a `fork` remote
   exists.
2. **Check the target working tree:** `git -C <target> status --short`. A shared/public repo
   is frequently **dirty with unrelated work-in-progress**. If so, you MUST stage only the
   app's paths later — **never `git add -A` in the target**.
3. **Confirm it's safe to publish.** The app must ship **no** secrets, credentials, tokens,
   API keys, or private user data. (Well-built apps keep those in the host OAuth store or the
   user's `%APPDATA%`, not the repo.) For a public target this is mandatory — grep the app
   folder if unsure; if anything sensitive is baked in, stop and tell the user.
4. **Preserve the app id.** The folder name equals `app.json.id`. Changing the id orphans
   installs, the host OAuth provider (`app:<id>`), editor page references, and the app's
   `%APPDATA%\bedrock-panel\<id>` data dir. Keep it identical across the move.

## Move procedure

Let `SRC` = source repo path, `DST` = target repo path, `<id>` = the app id.

1. **Copy the app** (and any authoring skill it owns) into the target:
   ```bash
   cp -r "$SRC/community-apps/<id>" "$DST/community-apps/<id>"
   # if the app ships a skill:
   cp -r "$SRC/community-apps/skills/<skill>" "$DST/community-apps/skills/<skill>"
   ```
2. **Migration-time manifest edits** (in the target copy): bump `app.json` version per the
   target repo's scheme, and apply any move-time change the user asked for (e.g. adding
   `oauth.selfManaged: true`). Then validate:
   ```bash
   node -e "JSON.parse(require('fs').readFileSync('$DST/community-apps/<id>/app.json','utf8'))"
   node --check "$DST/community-apps/<id>/server.js"   # and app.js, and any other JS
   node "$DST/community-apps/<id>/test.js"             # if the app has a test
   ```
3. **Build the zip and rebuild the index** in the target. The zip's internal paths are
   `<id>/`-prefixed and list exactly the app's shipped files (check the app's existing zip or
   its file set — typically app.json, index.html, app.js, server.js, plus any engine modules):
   ```bash
   cd "$DST" && python -c "
   import zipfile
   files = ['app.json','index.html','app.js','server.js', ...]  # the app's actual files
   with zipfile.ZipFile('community-apps/<id>.zip','w',zipfile.ZIP_DEFLATED) as z:
       for f in files: z.write('community-apps/<id>/'+f, '<id>/'+f)
   "
   node tools/build-community-index.js
   ```
4. **Verify the index diff adds ONLY this app:**
   `git -C "$DST" diff --stat community-apps/index.json` (expect a small insertion), and
   confirm the added entry is `<id>`. If other apps changed, the target had manifest edits in
   its WIP — investigate before committing.
5. **Stage only the app's paths, verify, commit, push** to the target's own remote/branch:
   ```bash
   git -C "$DST" add community-apps/<id> community-apps/<id>.zip \
                     community-apps/skills/<skill> community-apps/index.json
   git -C "$DST" diff --cached --name-only          # MUST be only the paths above
   git -C "$DST" status --short | grep -v '^[AM] '   # confirm the WIP is still unstaged
   git -C "$DST" commit -m "Add <Name> drop-in app (<id> vX.Y.Z)"
   git -C "$DST" push origin main                    # explicit remote — not 'fork'
   ```
6. **Remove from the source** (only if moving, not copying — this is the user's decision):
   ```bash
   git -C "$SRC" rm -r community-apps/<id> community-apps/<id>.zip community-apps/skills/<skill>
   (cd "$SRC" && node tools/build-community-index.js)   # index now omits <id>
   git -C "$SRC" add -A && git -C "$SRC" commit -m "Remove <Name> — migrated to <target repo>"
   git -C "$SRC" push origin <branch>
   ```
   (`git add -A` is safe in the *source* — it's the user's own dev repo; the WIP hazard is a
   target-repo concern.)

## After the move

- The user re-points their Bedrock Panel **"Browse repo"** (the community-apps source it polls
  for updates) to the **target** repo, so the app keeps updating from its new home. The
  already-installed app keeps running; only the update source changes.
- The editor installs from the target's GitHub main — the user reloads the app page after the
  next update to pick up changes (local commits are invisible until pushed).

## Gotchas (learned the hard way)

- **The `fork` remote trap.** Public Bedrock Panel clones carry a `fork` remote to the upstream
  they branched from. `git push` with the wrong default, or a careless `git push fork`, sends
  the user's app to someone else's repo. Always push to `origin` explicitly and re-check with
  `git log origin/main --oneline -1` after.
- **Never `git add -A` in a dirty target.** Staging the target's unrelated WIP into your app
  commit is the most likely mistake. Add the app's paths by name and verify `--cached`.
- **CRLF/LF warnings are normal.** Repos with different `.gitattributes`/`autocrlf` emit
  "LF will be replaced by CRLF" (or the reverse) on staging — harmless normalization, not an
  error.
- **Don't touch host/runtime files.** A migration only moves `community-apps/<id>/` (+ its
  skill, index, zip). Editing `app/*`, `src/*`, packaging, or docs is platform work, out of
  scope unless the user explicitly asks.
- **Version scheme is the target repo's.** Follow the destination repo's convention for the
  bump, not the source's.

## Verify

1. Target `community-apps/index.json` lists `<id>` at the new version; `<id>.zip` sits next
   to the app folder; `git log origin/main -1` on the target shows your commit.
2. Source no longer lists `<id>` (for a move); its other apps are intact.
3. The user can install/update the app from the target repo.
